### 一、权限架构

系统采用 **RBAC（基于角色的访问控制）+ ABAC（基于属性的访问控制）** 混合架构：

- **RBAC**: 基于角色的权限控制，管理用户可以执行的操作
- **ABAC**: 基于部门（dept_key）的数据访问范围控制，管理用户可以访问的数据
- **Text2SQL 权限**: 基于 Text2SQL 功能的访问控制和数据脱敏

---

### 二、角色定义 (Role)

系统定义了三种全局角色：

| 角色   | 角色标识 | 说明                                     |
| ------ | -------- | ---------------------------------------- |
| 管理员 | `admin`  | 拥有所有权限，不受部门限制           |
| 数据分析师 | `analyst` | 可以使用 Text2SQL 功能，访问 analytics 数据集 |
| 普通用户 | `member`  | 普通用户，部门权限由数据库控制             |

**重要说明**：
- `editor` 和 `viewer` 不再是全局角色，而是部门级别的权限
- 部门级别的权限通过 `user_departments` 表的 `can_read` 和 `can_write` 字段控制
  - `editor` 相当于 `can_read=1, can_write=1`
  - `viewer` 相当于 `can_read=1, can_write=0`

权限点采用 `资源:操作:子操作` 的命名规范：

### 五、Text2SQL 权限控制

#### 1. 数据脱敏规则

**列敏感级别**：

| 级别 | 说明 | 示例 | 脱敏方式 |

### 六、部门访问控制 (Dept Scope)

#### 1. 数据模型

每个用户关联一个 `user_departments` 列表，定义了该用户可以访问的部门范围，以及在每个部门的读写权限。

```python
# 示例：用户-部门映射（演示数据，实际应从数据库读取）
_DEMO_USER_DEPT_ACCESS: dict[str, list[dict]] = {
    "user-editor": [
        {"dept_key": "micro_service", "dept_role": "editor", "can_write": 1},  # 管理员权限
        {"dept_key": "AI", "dept_role": "viewer", "can_write": 0}        # 只读权限
    ],
    "user-viewer": [
        {"dept_key": "AI", "dept_role": "viewer", "can_write": 0}  # 只读权限
    ],
}
```

**重要说明**：
- `admin` 角色的用户拥有所有部门的完全访问权限，无需在 `user_departments` 表中配置
- `member` 和 `analyst` 角色的用户需要通过 `user_departments` 表配置具体部门的访问权限
- 部门权限仅影响知识库文件访问，不影响 Text2SQL 权限

#### 2. 读权限检查 - `can_access_dept()`

**适用场景**：文件列表、文件详情、文件下载、搜索

**规则**：

- `admin`: 可以访问所有部门（返回 `True`），无需检查数据库
- `member` / `analyst`: 只能访问 `user_departments` 表中配置的部门

```python
def can_access_dept(user: dict[str, Any], dept_key: str) -> bool:
    # admin不受部门限制
    if has_role(user, ROLE_ADMIN):
        return True
    
    # 检查用户是否对该部门有读权限
    try:
        dept_access = RBACDAO.get_user_departments(int(user["user_id"]))
        for dept in dept_access:
            if dept['dept_key'] == dept_key and dept['can_read']:
                return True
    except Exception as e:
        logger.error(f"Failed to check department read permission: {e}")
    return False
```

#### 3. 写权限检查 - `can_write_dept()`

**适用场景**：文件上传、文件编辑、文件删除

**规则**：

- `admin`: 可以操作所有部门，无需检查数据库
- `member` / `analyst`: 只能操作 `can_write=1` 且 `dept_role='editor'` 的部门

```python
def can_write_dept(user: dict[str, Any], dept_key: str) -> bool:
    if has_role(user, ROLE_ADMIN):
        return True
    
    # 检查用户是否对该部门有写权限（editor 角色）
    try:
        dept_access = RBACDAO.get_user_departments(int(user["user_id"]))
        for dept in dept_access:
            if dept['dept_key'] == dept_key and dept['can_write']:
                return True
    except Exception as e:
        logger.error(f"Failed to check department write permission: {e}")
    return False
```

#### 1. 认证 (Authentication) - 验证"你是谁"

**流程**：

1. 用户登录时，后端验证用户名和密码
2. 生成 JWT token，包含 `sub`（用户ID）、`roles`（角色列表，可以是 admin, member, analyst）、`exp`（过期时间）
3. Token 通过 HTTP-only Cookie 传输

**函数**：
- `create_access_token(sub, roles)`: 生成 JWT token
- `get_current_user(request)`: 从 Cookie 解析 token，返回用户身份

**JWT Payload 结构**：
```json
{
  "sub": "user-ryan",
  "roles": ["admin"],
  "iat": 1736136800,
  "exp": 1736741600
}
```

#### 2. 授权 (Authorization) - 验证"你能做什么"

**流程**：
1. `get_user_context()`: 构建完整的用户上下文
   - 从 JWT 获取 `user_id` 和 `roles`（可以是 admin, member, analyst）
   - 从数据库获取 `permissions`（用户的所有权限点）
   - 从数据库获取 `allowed_dept_keys`（用户有读权限的部门）
   - 新增：从数据库获取 Text2SQL 权限信息
2. 在接口层使用权限检查函数或依赖注入进行验证

**用户上下文结构**：

### 八、权限检查函数

#### 1. `has_role(user, role)`
检查用户是否拥有指定角色

#### 2. `require_admin(user)`
检查用户是否有管理员权限，没有则抛出 403 异常

检查用户是否可以访问指定部门（读权限）

检查用户是否具有指定权限点（RBAC）
- 如果用户任一角色拥有该权限，则通过

### 十一、安全注意事项

1. **角色清洗**: 创建 token 时过滤非标准角色，防止角色注入攻击（只保留 admin、member、analyst）
2. **Token 存储**: JWT 存储在 HTTP-only Cookie，防止 XSS 攻击
3. **权限最小化**: 默认遵循"最小权限原则"，用户只能访问必要的资源
4. **404 vs 403**: 文件不存在和无权限统一返回 404，防止信息泄露
5. **数据隔离**: 基于部门的数据隔离在应用层实现，防止越权访问
6. **部门权限控制**: 部门级别的读写权限由数据库的 `can_read` 和 `can_write` 字段控制，确保细粒度权限管理
7. **Text2SQL 安全**:
   - 只允许 SELECT 查询（禁止 INSERT、UPDATE、DELETE、DDL）
   - analyst 角色强制 LIMIT 限制（默认 2000，最大 10000）
   - admin 无 LIMIT 限制
   - PII 数据部分遮蔽（邮箱、手机号、姓名等）
   - 敏感数据完全隐藏（薪资、绩效等）
   - 通过视图实现数据库层面的脱敏

### 十三、Text2SQL 权限与 SQL RAG 过滤详解

#### 1. 权限检查流程

Text2SQL 功能的权限检查在以下三个阶段进行：

##### 1.1 路由阶段 - `resolve_target_db` 节点

```python
# 检查用户是否有 Text2SQL 使用权限
can_use_text2sql = user_context.get("can_use_text2sql", False)
if not can_use_text2sql:
    return {"target_db": db, "error": "您没有使用 Text2SQL 的权限，请联系管理员"}

# 检查数据库访问权限
allowed_databases = user_context.get("text2sql_allowed_databases", [])
if db not in allowed_databases:
    return {"target_db": db, "error": f"您无权访问数据库: {db}"}

# 判断是否使用 analytics 视图
use_analytics_views = should_use_analytics_views(
    user_context.get("roles", []), user_context.get("permissions", set())
)
```

**规则**：
- admin: 可访问 `['ecommerce']`（原始数据库），`use_analytics_views = False`
- analyst: 可访问 `['ecommerce']`（analytics 视图），`use_analytics_views = True`
- member: 无权限

##### 1.2 Schema 检索阶段 - `retrieve_sql_schema` 节点

```python
# 获取允许访问的表列表（基于列敏感度）
allowed_tables = Text2SQLPermissionDAO.get_allowed_tables_for_user(db, roles)

# 构建 Milvus 检索过滤表达式
expr = _build_schema_filter(db, allowed_tables)
```

**过滤表达式构建规则**：
```python
def _build_schema_filter(db: str, allowed_tables: list[str] | None) -> str:
    # 基础过滤：只检索 ddl 和 description 类型的文档
    base_expr = f'metadata["doc_type"] in ["ddl", "description"]'

    # 添加数据库过滤
    if db:
        base_expr += f' and metadata["database"] == "{db}"'

    # 如果有表权限限制，添加表名过滤
    if allowed_tables:
        table_filter = " or ".join(
            [f'metadata["table_name"] == "{t}"' for t in allowed_tables]
        )
        base_expr += f" and ({table_filter})"

    return base_expr
```

#### 2. SQL RAG 过滤实现

##### 2.1 表级访问控制 - `get_allowed_tables_for_user()`

```python
@staticmethod
def get_allowed_tables_for_user(db_name: str, user_roles: List[str]) -> List[str]:
    """
    获取用户可访问的表列表

    策略:
    - admin: 可访问所有表（返回空列表表示无限制）
    - analyst: 只能访问 public 和 internal 级别的列所在的表
    - member: 不能使用 text2sql (在 API 层拦截)

    Returns:
        表名列表，空列表表示无限制
    """
    # admin 无限制
    if "admin" in user_roles:
        return []

    # analyst 只能访问非敏感数据
    try:
        with get_db_connection() as conn:
            with conn.cursor() as cursor:
                cursor.execute(
                    """
                    SELECT DISTINCT table_name
                    FROM column_sensitivity_tags
                    WHERE database_name = %s
                    AND sensitivity_level IN ('public', 'internal')
                    """,
                    (db_name,),
                )
                return [row[0] for row in cursor.fetchall()]
    except Exception as e:
        logger.error(f"Failed to get allowed tables: {e}")
        return []
```

**核心逻辑**：
1. admin 角色：返回空列表（表示无限制，可以检索所有表）
2. analyst 角色：查询 `column_sensitivity_tags` 表，只返回包含 `public` 或 `internal` 级别列的表
3. member 角色：在 API 层已经被拦截，不会进入此函数

##### 2.2 列敏感度查询 - `column_sensitivity_tags` 表

```sql
CREATE TABLE column_sensitivity_tags (
    id INT AUTO_INCREMENT PRIMARY KEY,
    database_name VARCHAR(100) NOT NULL,
    table_name VARCHAR(100) NOT NULL,
    column_name VARCHAR(100) NOT NULL,
    sensitivity_level ENUM('public', 'internal', 'pii', 'sensitive') NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_column (database_name, table_name, column_name)
);
```

**敏感级别说明**：
- **public**: 公开数据，不脱敏
- **internal**: 内部数据，不脱敏
- **pii**: 个人身份信息，部分遮蔽
- **sensitive**: 敏感数据，完全隐藏

##### 2.3 Milvus 检索过滤

在 Milvus 中检索 Schema 文档时，通过表达式过滤来控制文档检索范围：

```python
# admin 的过滤表达式（无表限制）
'metadata["doc_type"] in ["ddl", "description"] and metadata["database"] == "ecommerce"'

# analyst 的过滤表达式（有表限制）
'metadata["doc_type"] in ["ddl", "description"] and metadata["database"] == "ecommerce" and (metadata["table_name"] == "products" or metadata["table_name"] == "orders" or ...)'
```

**效果**：

- admin: 可以检索到所有表的 schema 文档
- analyst: 只能检索到包含 public/internal 级别列的表的 schema 文档
- LLM 生成的 SQL 不会包含没有 schema 文档的表名

#### 3. 数据脱敏实现

##### 3.1 结果脱敏 - `mask_query_result()`

```python
def mask_query_result(
    result: List[Dict[str, Any]], db_name: str, table_name: str, user_roles: List[str] = None
) -> List[Dict[str, Any]]:
    """
    对查询结果进行列脱敏

    策略:
    - admin: 不脱敏
    - analyst: 脱敏 pii 和 sensitive 列
    - public/internal: 不脱敏
    """
    if not result:
        return result

    # admin 不脱敏
    if user_roles and "admin" in user_roles:
        return result

    # 获取列的敏感级别
    sensitivity_map = Text2SQLPermissionDAO.get_table_columns_sensitivity(db_name, table_name)

    if not sensitivity_map:
        return result

    masked_result = []
    for row in result:
        masked_row = {}
        for col, val in row.items():
            if col in sensitivity_map:
                level = sensitivity_map[col]
                if level == "pii" and val:
                    masked_row[col] = mask_pii(val)
                elif level == "sensitive" and val:
                    masked_row[col] = "[SENSITIVE]"
                else:
                    masked_row[col] = val
            else:
                masked_row[col] = val
        masked_result.append(masked_row)

    return masked_result
```

##### 3.2 PII 部分遮蔽 - `mask_pii()`

```python
def mask_pii(value: Any) -> str:
    """
    PII 数据部分遮蔽

    保留前几位和后几位，中间用 **** 替换

    Examples:
        >>> mask_pii('zhangsan@example.com')
        'zh***com'
        >>> mask_pii('13812345678')
        '13***78'
        >>> mask_pii('张三')
        '张***'
    """
    if not value:
        return value

    val_str = str(value).strip()

    if len(val_str) <= 4:
        return "****"
    elif len(val_str) <= 8:
        head_len = 2
        tail_len = 2
    else:
        head_len = 3
        tail_len = 4

    return f"{val_str[:head_len]}****{val_str[-tail_len:]}"
```

#### 7. 安全设计要点

1. **多层防护**：
   - API 层：检查用户是否有 Text2SQL 使用权限
   - RAG 层：过滤 schema 检索结果
   - 执行层：数据脱敏

2. **最小权限原则**：
   - analyst 只能访问包含 public/internal 列的表
   - 敏感数据（pii/sensitive）在结果层进行脱敏

3. **白名单机制**：
   - 通过 Milvus 过滤表达式实现白名单过滤
   - 未被允许的表不会被检索，LLM 无法生成相关 SQL

4. **审计友好**：
   - 列敏感度存储在数据库中，便于审计和管理
   - 角色权限集中管理，便于快速调整
