### 一、权限架构

系统采用 **RBAC（基于角色的访问控制）+ ABAC（基于属性的访问控制）** 混合架构：

- **RBAC**: 基于角色的权限控制，管理用户可以执行的操作
- **ABAC**: 基于部门（dept_key）的数据访问范围控制，管理用户可以访问的数据

---

### 二、角色定义 (Role)

系统定义了三种标准角色，层级从高到低：

| 角色   | 角色标识 | 说明                                     |
| ------ | -------- | ---------------------------------------- |
| 管理员 | `admin`  | 拥有所有权限，不受部门限制               |
| 编辑者 | `editor` | 可查看、下载、上传知识库文件，受部门限制 |
| 查看者 | `viewer` | 只能查看和下载知识库文件，受部门限制     |

---

### 三、权限点定义 (Permissions)

权限点采用 `资源:操作:子操作` 的命名规范：

#### 知识库权限

| 权限标识           | 权限说明       | 适用角色              |
| ------------------ | -------------- | --------------------- |
| `kb:file:list`     | 列出知识库文件 | admin, editor, viewer |
| `kb:file:detail`   | 查看文件详情   | admin, editor, viewer |
| `kb:file:download` | 下载文件       | admin, editor, viewer |
| `kb:file:upload`   | 上传/编辑文件  | admin, editor         |

#### 管理员权限

| 权限标识            | 权限说明     | 适用角色 |
| ------------------- | ------------ | -------- |
| `admin:user:list`   | 列出所有用户 | admin    |
| `admin:user:update` | 更新用户信息 | admin    |

---

### 四、角色-权限映射

```python
ROLE_PERMS: dict[str, set[str]] = {
    ROLE_ADMIN: {
        # 知识库权限
        PERM_KB_FILE_LIST, 
        PERM_KB_FILE_DETAIL, 
        PERM_KB_FILE_DOWNLOAD, 
        PERM_KB_FILE_UPLOAD,
        # 管理员权限
        PERM_ADMIN_USER_LIST, 
        PERM_ADMIN_USER_UPDATE,
    },
    ROLE_EDITOR: {
        PERM_KB_FILE_LIST, 
        PERM_KB_FILE_DETAIL, 
        PERM_KB_FILE_DOWNLOAD, 
        PERM_KB_FILE_UPLOAD,
    },
    ROLE_VIEWER: {
        PERM_KB_FILE_LIST, 
        PERM_KB_FILE_DETAIL, 
        PERM_KB_FILE_DOWNLOAD,
    },
}
```

**权限继承规则**：
- 用户可以拥有多个角色，权限为所有角色权限的并集
- `admin` 角色自动拥有所有权限
- 角色在 JWT token 中以数组形式传递

### 五、部门访问控制 (Dept Scope)

#### 1. 数据模型

每个用户关联一个 `allowed_dept_keys` 列表，定义了该用户可以访问的部门范围。

```python
# 示例：用户-部门映射（演示数据，实际应从数据库读取）
_DEMO_ALLOWED_DEPT_KEYS: dict[str, list[str]] = {
    "user-ryan": ["micro_service"],
    "user-viewer": ["AI"],
}
```

#### 2. 读权限检查 - `can_access_dept()`

**适用场景**：文件列表、文件详情、文件下载、搜索

**规则**：

- `admin`: 可以访问所有部门（返回 `True`）
- `editor` / `viewer`: 只能访问 `allowed_dept_keys` 中的部门

```python
def can_access_dept(user: dict[str, Any], dept_key: str) -> bool:
    if has_role(user, ROLE_ADMIN):
        return True
    allowed = set(user.get("allowed_dept_keys") or [])
    return dept_key in allowed
```

#### 3. 写权限检查 - `can_upload_dept()`

**适用场景**：文件上传、文件编辑

**规则**：
- `admin`: 可以操作所有部门
- `editor`: 只能操作 `allowed_dept_keys` 中的部门
- `viewer`: 不允许（但通常会被 `require_perm(PERM_KB_FILE_UPLOAD)` 提前拦截）

```python
def can_upload_dept(user: dict[str, Any], dept_key: str) -> bool:
    if has_role(user, ROLE_ADMIN):
        return True
    if has_role(user, ROLE_EDITOR):
        allowed = set(user.get("allowed_dept_keys") or [])
        return dept_key in allowed
    return False
```

### 六、认证与授权流程

#### 0. JWT认证流程图

```txt
浏览器         前端代码                FastAPI 后端
  |                |                       |
  |  1. 输入用户名密码                     |
  |---------------->|                       |
  |                |  2. POST /auth/login  |
  |                |----------------------->|
  |                |                       |  3. 验证用户名密码
  |                |                       |  4. 生成 JWT Token
  |                |                       |  5. 设置 Set-Cookie
  |                |<-----------------------|
  |                |  6. 200 OK             |
  |<----------------|                       |
  |  7. 自动存储 Cookie                       |
  |                                        |
  |  8. 点击"知识库"                        |
  |---------------->|                       |
  |                |  9. GET /kb/files    |
  |                | (自动携带 Cookie)------>|
  |                |                       |  10. get_user_context()
  |                |                       |     ├─ get_current_user()
  |                |                       |     │  └─ jwt.decode()
  |                |                       |     └─ 查询 allowed_dept_keys
  |                |                       |  11. require_perm()
  |                |                       |  12. 业务逻辑处理
  |                |                       |  13. 过滤文件列表
  |                |<-----------------------|
  |                |  14. 200 OK + 数据     |
  |<----------------|                       |
  |  15. 显示文件列表                       |
```



#### 1. 认证 (Authentication) - 验证"你是谁"

**流程**：

1. 用户登录时，后端验证用户名和密码
2. 生成 JWT token，包含 `sub`（用户ID）、`roles`（角色列表）、`exp`（过期时间）
3. Token 通过 HTTP-only Cookie 传输

**函数**：
- `create_access_token(sub, roles)`: 生成 JWT token
- `get_current_user(request)`: 从 Cookie 解析 token，返回用户身份

**JWT Payload 结构**：
```json
{
  "sub": "user-ryan",
  "roles": ["admin"],
  "iat": 1736136800,
  "exp": 1736741600
}
```

#### 2. 授权 (Authorization) - 验证"你能做什么"

**流程**：
1. `get_user_context()`: 构建完整的用户上下文
   - 从 JWT 获取 `user_id` 和 `roles`
   - 从数据库获取 `allowed_dept_keys`
2. 在接口层使用权限检查函数或依赖注入进行验证

**用户上下文结构**：
```python
class UserContext(TypedDict):
    user_id: str
    roles: list[str]
    allowed_dept_keys: list[str]
```

### 七、权限检查函数

#### 1. `has_role(user, role)`
检查用户是否拥有指定角色

#### 2. `require_perm(user, perm)`
检查用户是否拥有指定权限点（RBAC）
- 如果用户任一角色拥有该权限，则通过
- 否则抛出 `403 Forbidden`

#### 3. `can_access_dept(user, dept_key)`
检查用户是否可以访问指定部门（读权限）

#### 4. `can_upload_dept(user, dept_key)`
检查用户是否可以上传/编辑指定部门的文件（写权限）

#### 5. `require_permission(perm)`
FastAPI 依赖注入版本，可直接在接口声明中使用
```python
@kb_router.get("/files")
async def list_files(
    user: dict = Depends(require_permission(PERM_KB_FILE_LIST))
):
    ...
```

### 十、安全注意事项

1. **角色清洗**: 创建 token 时过滤非标准角色，防止角色注入攻击
2. **Token 存储**: JWT 存储在 HTTP-only Cookie，防止 XSS 攻击
3. **权限最小化**: 默认遵循"最小权限原则"，用户只能访问必要的资源
4. **404 vs 403**: 文件不存在和无权限统一返回 404，防止信息泄露
5. **数据隔离**: 基于部门的数据隔离在应用层实现，防止越权访问

### 十一、扩展建议

1. **权限粒度细化**: 可按文件类型、文件大小等维度进一步细分权限
2. **动态权限**: 未来可支持基于用户属性的动态权限（如部门领导可以查看下属文件）
3. **审计日志**: 记录关键操作（如文件下载、上传）的审计日志
4. **权限缓存**: 使用 Redis 缓存用户权限，减少数据库查询
5. **权限继承**: 支持部门层级，子部门继承父部门权限
