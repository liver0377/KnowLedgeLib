### 一、权限架构

系统采用 **RBAC（基于角色的访问控制）+ ABAC（基于属性的访问控制）** 混合架构：

- **RBAC**: 基于角色的权限控制，管理用户可以执行的操作
- **ABAC**: 基于部门（dept_key）的数据访问范围控制，管理用户可以访问的数据

---

### 二、角色定义 (Role)

系统定义了两种全局角色：

| 角色   | 角色标识 | 说明                                     |
| ------ | -------- | ---------------------------------------- |
| 管理员 | `admin`  | 拥有所有权限，不受部门限制               |
| 普通用户 | `member`  | 普通用户，部门权限由数据库控制             |

**重要说明**：
- `editor` 和 `viewer` 不再是全局角色，而是部门级别的权限
- 部门级别的权限通过 `user_departments` 表的 `can_read` 和 `can_write` 字段控制
  - `editor` 相当于 `can_read=1, can_write=1`
  - `viewer` 相当于 `can_read=1, can_write=0`

---

### 三、权限点定义 (Permissions)

权限点采用 `资源:操作:子操作` 的命名规范：

#### 知识库权限

| 权限标识           | 权限说明       | 适用角色              |
| ------------------ | -------------- | --------------------- |
| `kb:file:list`     | 列出知识库文件 | admin, member        |
| `kb:file:detail`   | 查看文件详情   | admin, member        |
| `kb:file:download` | 下载文件       | admin, member        |
| `kb:file:upload`   | 上传/编辑文件  | admin, member (需要部门写权限)  |
| `kb:file:delete`   | 删除文件       | admin, member (需要部门写权限)  |

#### 管理员权限

| 权限标识            | 权限说明     | 适用角色 |
| ------------------- | ------------ | -------- |
| `admin:user:list`   | 列出所有用户 | admin    |
| `admin:user:update` | 更新用户信息 | admin    |
| `admin:dept:create` | 创建部门     | admin    |

### 五、部门访问控制 (Dept Scope)

#### 1. 数据模型

每个用户关联一个 `user_departments` 列表，定义了该用户可以访问的部门范围，以及在每个部门的读写权限。

```python
# 示例：用户-部门映射（演示数据，实际应从数据库读取）
_DEMO_USER_DEPT_ACCESS: dict[str, list[dict]] = {
    "user-editor": [
        {"dept_key": "micro_service", "dept_role": "editor", "can_write": 1},  # 管理员权限
        {"dept_key": "AI", "dept_role": "viewer", "can_write": 0}        # 只读权限
    ],
    "user-viewer": [
        {"dept_key": "AI", "dept_role": "viewer", "can_write": 0}  # 只读权限
    ],
}
```

**重要说明**：
- `admin` 角色的用户拥有所有部门的完全访问权限，无需在 `user_departments` 表中配置
- `member` 角色的用户需要通过 `user_departments` 表配置具体部门的访问权限

#### 2. 读权限检查 - `can_access_dept()`

**适用场景**：文件列表、文件详情、文件下载、搜索

**规则**：

- `admin`: 可以访问所有部门（返回 `True`），无需检查数据库
- `member`: 只能访问 `user_departments` 表中配置的部门

```python
def can_access_dept(user: dict[str, Any], dept_key: str) -> bool:
    if has_role(user, ROLE_ADMIN):
        return True
    
    # 检查用户是否在该部门的访问列表中
    try:
        dept_access = RBACDAO.get_user_departments(int(user["user_id"]))
        for dept in dept_access:
            if dept['dept_key'] == dept_key:
                return True
    except Exception as e:
        logger.error(f"Failed to check department read permission: {e}")
    return False
```

#### 3. 写权限检查 - `can_write_dept()`

**适用场景**：文件上传、文件编辑、文件删除

**规则**：
- `admin`: 可以操作所有部门，无需检查数据库
- `member`: 只能操作 `can_write=1` 且 `dept_role='editor'` 的部门

```python
def can_write_dept(user: dict[str, Any], dept_key: str) -> bool:
    if has_role(user, ROLE_ADMIN):
        return True
    
    # 检查用户是否对该部门有写权限（editor 角色）
    try:
        dept_access = RBACDAO.get_user_departments(int(user["user_id"]))
        for dept in dept_access:
            if dept['dept_key'] == dept_key and dept['can_write'] == 1:
                return True
    except Exception as e:
        logger.error(f"Failed to check department write permission: {e}")
    return False
```

### 六、认证与授权流程

#### 0. JWT认证流程图

```txt
浏览器         前端代码                FastAPI 后端
  |                |                       |
  |  1. 输入用户名密码                     |
  |---------------->|                       |
  |                |  2. POST /auth/login  |
  |                |----------------------->|
  |                |                       |  3. 验证用户名密码
  |                |                       |  4. 生成 JWT Token
  |                |                       |     - roles: ["admin"] 或 ["member"]
  |                |                       |  5. 设置 Set-Cookie
  |                |<-----------------------|
  |                |  6. 200 OK             |
  |<----------------|                       |
  |  7. 自动存储 Cookie                       |
  |                                        |
  |  8. 点击"知识库"                        |
  |---------------->|                       |
  |                |  9. GET /kb/files    |
  |                | (自动携带 Cookie)------>|
  |                |                       |  10. get_user_context()
  |                |                       |     ├─ get_current_user()
  |                |                       |     │  └─ jwt.decode()
  |                |                       |     ├─ 查询 roles
  |                |                       |     ├─ 查询 permissions
  |                |                       |     └─ 查询 user_departments (can_read, can_write)
  |                |                       |  11. require_permission()
  |                |                       |  12. 业务逻辑处理
  |                |                       |  13. 过滤文件列表（检查 can_access_dept）
  |                |<-----------------------|
  |                |  14. 200 OK + 数据     |
  |<----------------|                       |
  |  15. 显示文件列表                       |
```

#### 1. 认证 (Authentication) - 验证"你是谁"

**流程**：

1. 用户登录时，后端验证用户名和密码
2. 生成 JWT token，包含 `sub`（用户ID）、`roles`（角色列表，只能是 admin 或 member）、`exp`（过期时间）
3. Token 通过 HTTP-only Cookie 传输

**函数**：
- `create_access_token(sub, roles)`: 生成 JWT token
- `get_current_user(request)`: 从 Cookie 解析 token，返回用户身份

**JWT Payload 结构**：
```json
{
  "sub": "user-ryan",
  "roles": ["admin"],
  "iat": 1736136800,
  "exp": 1736741600
}
```

#### 2. 授权 (Authorization) - 验证"你能做什么"

**流程**：
1. `get_user_context()`: 构建完整的用户上下文
   - 从 JWT 获取 `user_id` 和 `roles`（只能是 admin 或 member）
   - 从数据库获取 `permissions`（用户的所有权限点）
   - 从数据库获取 `allowed_dept_keys`（用户有读权限的部门）
2. 在接口层使用权限检查函数或依赖注入进行验证

**用户上下文结构**：
```python
class UserContext(TypedDict):
    user_id: str
    roles: list[str]
    allowed_dept_keys: list[str]
    permissions: set[str]
```

### 七、权限检查函数

#### 1. `has_role(user, role)`
检查用户是否拥有指定角色

#### 2. `require_admin(user)`
检查用户是否有管理员权限，没有则抛出 403 异常

#### 3. `can_access_dept(user, dept_key)`
检查用户是否可以访问指定部门（读权限）
- `admin` 角色直接返回 True
- `member` 角色从数据库查询用户的部门权限
- 检查用户是否在该部门的访问列表中

#### 4. `can_write_dept(user, dept_key)`
检查用户是否可以上传/编辑/删除指定部门的文件（写权限）
- `admin` 角色直接返回 True
- `member` 角色从数据库查询用户的部门权限
- 检查 `can_write=1` 且 `dept_role='editor'`

#### 5. `permission_manager.require_permission(user, resource, action)`
检查用户是否具有指定权限点（RBAC）
- 如果用户任一角色拥有该权限，则通过
- 否则抛出 `403 Forbidden`

### 十、安全注意事项

1. **角色清洗**: 创建 token 时过滤非标准角色，防止角色注入攻击（只保留 admin 和 member）
2. **Token 存储**: JWT 存储在 HTTP-only Cookie，防止 XSS 攻击
3. **权限最小化**: 默认遵循"最小权限原则"，用户只能访问必要的资源
4. **404 vs 403**: 文件不存在和无权限统一返回 404，防止信息泄露
5. **数据隔离**: 基于部门的数据隔离在应用层实现，防止越权访问
6. **部门权限控制**: 部门级别的读写权限由数据库的 `can_read` 和 `can_write` 字段控制，确保细粒度权限管理

### 十一、扩展建议

1. **权限粒度细化**: 可按文件类型、文件大小等维度进一步细分权限
2. **动态权限**: 未来可支持基于用户属性的动态权限（如部门领导可以查看下属文件）
3. **审计日志**: 记录关键操作（如文件下载、上传）的审计日志
4. **权限缓存**: 使用 Redis 缓存用户权限，减少数据库查询
5. **权限继承**: 支持部门层级，子部门继承父部门权限
6. **批量权限管理**: 提供管理员批量设置用户部门权限的接口

### 十二、权限迁移说明

如果从旧版本的权限系统迁移：

1. **角色迁移**：
   - 所有 `editor` 角色用户应改为 `member` 角色
   - 所有 `viewer` 角色用户应改为 `member` 角色
   - `admin` 角色保持不变

2. **部门权限迁移**：
   - 旧的 `editor` 角色：在对应部门设置 `dept_role='editor', can_write=1`
   - 旧的 `viewer` 角色：在对应部门设置 `dept_role='viewer', can_write=0`

3. **数据库迁移**：
   - 执行新的 `rbac_schema.sql` 创建新的表结构
   - 执行 `rbac_seed_data.sql` 初始化新的角色和权限数据
   - 更新 `user_roles` 表中的角色数据（editor/viewer -> member）
   - 更新 `user_departments` 表中的权限数据（根据用户的旧角色设置 dept_role 和 can_write）

4. **权限管理界面调整**：
   - 删除"系统角色"列和"管理员"、"普通用户"按钮
   - 系统管理员（admin）自动拥有所有部门的管理员权限，无需手动设置
   - 普通用户的部门权限通过"设置成管理员"按钮进行切换

详细迁移步骤请参考 `docs/RBAC数据库迁移说明.md`
